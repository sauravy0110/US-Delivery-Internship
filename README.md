# Support & TAM AI Tools — Ticket Triage and Account Health Briefs

Internal tooling for Technical Support and Technical Account Management teams:

1. **Ticket triage agent** (`app/triage.py`, `POST /triage`)
2. **TAM account health summariser** (`app/account_brief.py`, `GET /account-brief/{id}`)
3. **Evaluation harness** covering both (`eval/eval_harness.py`)
4. **Design note** (below)

Additional components: a Streamlit UI (`ui/streamlit_app.py`), a GitHub Actions workflow
that runs the eval harness on every push (`.github/workflows/eval.yml`), and prompt
versioning (`app.config.PROMPT_VERSIONS`).

**Retrieval, observability, and provider design:**
- **RAG**: SentenceTransformers embeddings + FAISS (`app/kb_retrieval.py`) as the primary
  retrieval backend, matching paraphrased tickets to KB docs semantically rather than by
  literal keyword overlap. Falls back to local TF-IDF automatically, with the fallback
  logged, if the embedding model can't be loaded.
- **Observability** (`app/observability.py`): every LLM call and retrieval-backend decision
  is written to `logs/events.jsonl` (latency, provider, success/failure, guardrail fallback
  events). `python scripts/observability_report.py` reports p50/p95 latency and failure
  counts per event type.
- **Provider-agnostic LLM client**: Groq, OpenAI, and Gemini are all reachable through the
  same OpenAI-compatible chat-completions call (`app/llm_client.py`); switching providers is
  a `.env` change.

---

## Dataset

`data/tickets.json` and `data/accounts.json` ship with a small sample dataset generated by
`scripts/generate_sample_data.py`, matching `DATA_SCHEMA.md`. To use a different dataset,
replace those two files and the contents of `knowledge-base/` — nothing else needs to change,
since all retrieval and lookups are schema-driven.

## Setup

```bash
pip install -r requirements.txt

cp .env.example .env
# Set LLM_PROVIDER (groq / openai / gemini / mock) and the matching API key.

python scripts/generate_sample_data.py   # only needed if data/ is empty
```

**LLM provider:** Groq, OpenAI, and Gemini are all OpenAI-wire-compatible, so
`app/llm_client.py` calls all three through one code path — provider choice is purely a
`.env` value (`LLM_PROVIDER=groq|openai|gemini|mock`). `mock` runs fully offline with a
deterministic rule-based fallback, no key required.

**KB retrieval:** defaults to SentenceTransformers + FAISS embeddings
(`KB_RETRIEVAL_MODE=embeddings`, downloads `all-MiniLM-L6-v2` on first run). Falls back to
local TF-IDF automatically if that download fails, or set `KB_RETRIEVAL_MODE=tfidf` to force
it explicitly.

```bash
uvicorn app.main:app --reload
```

## Running the eval harness

```bash
python -m eval.eval_harness
```

Writes `eval/eval_report.json` and `eval/eval_report.md`. Current run
(`LLM_PROVIDER=mock`, fully offline/deterministic):

```
Task 1 (triage):        6/6 passed, avg quality 1.0
Task 2 (account brief): 6/6 passed, avg quality 1.0
```

Each task has 6 test cases (5 required + 1 adversarial): the triage adversarial case is a
vague, near-content-free ticket that must still degrade to a valid enum value instead of
erroring; the account-brief adversarial case is an `account_id` with no matching record.
Scoring combines rule-based structural checks (valid enums, non-empty required fields, KB
match presence, determinism) with an LLM-as-judge pass on draft-response quality (falls back
to a heuristic judge in mock mode).

### Observability report

```bash
python scripts/observability_report.py
```

Reads `logs/events.jsonl` and prints call counts, failure counts, and p50/p95 latency per
event type — e.g. how often KB retrieval fell back from embeddings to TF-IDF, or how often
the LLM returned unparseable JSON and had to be guardrail-corrected.

## Design note

### Failure modes

1. **LLM returns malformed or off-schema JSON** (wrong enum value, missing field,
   hallucinated field name). *Mitigation:* `llm_client._extract_json` strips code fences
   and falls back to regex extraction; `triage.py` explicitly validates `issue_category`
   and `urgency_tier` against the allowed enums and substitutes a safe default (`Bug`/`P3`)
   rather than propagating invalid data downstream. *Detection:* every substitution is
   logged as a `triage.guardrail_fallback` event, so a rising fallback rate is visible as a
   metric; the eval harness also runs as a CI regression gate on every push.

2. **KB retrieval false positives/negatives, or a silent embedding-model degradation.**
   Even with embeddings, a ticket phrased very differently from the KB wording can miss a
   real match, and a coincidental overlap can surface an irrelevant doc. A subtler risk:
   when the embedding model can't be downloaded, some libraries fail by constructing an
   untrained model rather than raising cleanly — if that were ever mistaken for success,
   retrieval quality would degrade silently rather than falling back visibly. *Mitigation:*
   `_resolve_backend()` eagerly loads and exercises the model once at startup (not lazily on
   first query) so this class of failure surfaces immediately and is logged as
   `kb.backend_fallback`. A similarity floor (`min_score`) additionally suppresses
   low-confidence matches in either backend.

3. **Account-brief hallucination of risk signals or quotes not present in the source data**
   — the single biggest trust risk for a tool TAMs act on directly. *Mitigation:* the prompt
   requires every flag to carry a verbatim quote; the eval harness programmatically checks
   that each returned quote is a substring of the actual ticket/escalation-note text, so a
   fabricated quote fails the eval rather than reaching a TAM.

### Latency vs. quality trade-off

The concrete trade-off is in when the embedding index gets built: `_resolve_backend()`
eagerly encodes the entire KB and builds the FAISS index on first call, rather than lazily
on the first real query. The first request after a cold start pays extra latency so every
request after it doesn't — a support agent's first ticket of the day shouldn't be the one
that pays the index-build cost. If latency were the hard constraint, index building would
move to a background job on deploy/startup, decoupled from request handling, with TF-IDF
serving any request that arrives before the index is warm. If quality were the harder
constraint, the next lever isn't the embedding model — it's a hybrid BM25+embedding rerank,
since this KB's docs are dense with literal error codes that benefit from lexical matching
even alongside a good embedding model.

### Data sensitivity

Ticket bodies and account escalation notes can contain names, emails, or business-sensitive
language (churn risk, competitive intel). Sending that text to an external LLM API is a real
exposure. Mitigations: (1) `.env`-based key management keeps credentials out of the repo;
(2) a production version would add a pre-call PII redaction pass (regex plus a lightweight
NER pass for names/emails) before anything leaves the process, restoring redacted values in
the response, and would prefer a provider with a signed data-processing agreement and
zero-retention terms over a consumer-tier API; (3) `LLM_PROVIDER=mock` demonstrates the
architecture already supports a fully on-prem/local-model swap with no code changes
elsewhere.

### Scaling (10× ticket volume)

At 5,000 tickets: (1) the TF-IDF/embedding index is currently built in-memory on first call
via `@lru_cache` — fine at the current KB size, but if the KB itself also grows 10×, this
would move to a persisted index (e.g. a vector DB) rebuilt on a schedule rather than per
process start. (2) The account-brief cache (`lru_cache(maxsize=256)`) would start evicting
active accounts under real TAM traffic across 500 accounts — it would move to Redis with a
TTL keyed by the input hash, which is already how it's designed to key (content-hash, not
just account_id), so the interface wouldn't change. (3) The first thing to actually break is
LLM API rate limits: a free tier will throttle well before 5,000 tickets/day of triage
traffic — the fix is a request queue with backoff, and if traffic sustains, a paid tier or
batching multiple tickets into fewer, larger prompt calls where latency allows.
